## O problema

Um frontend compartilhado, uma hora, deixa de ser um problema técnico e vira
um problema de coordenação. Quando vários times contribuem para uma mesma
aplicação, cada release é a release de todo mundo: a mudança inacabada de um
time bloqueia a correção de outro, e a fila de deploy vira o verdadeiro
gargalo.

A Plataforma de Experiência do Desenvolvedor é a minha resposta à pergunta que
esse problema sempre faz — **como cinco times fazem deploy de forma
independente sem quebrar uns aos outros?** É um projeto pessoal que modela uma
plataforma interna do jeito que uma organização grande a operaria, construído
como um sistema que funciona, e não como um diagrama num slide, e é
[open source](https://github.com/lima300/developer-experience-platform).

## Restrições

- **Cada time controla o próprio ritmo de release.** Nada que um time publique
  pode exigir que outro time refaça build ou deploy.
- **Continua sendo um produto só.** Navegação, permissões e linguagem visual
  precisam parecer uma única aplicação, e não cinco sites costurados.
- **Uma falha fica local.** Um bug no código de um time não pode derrubar a
  página para todos os outros.

## Arquitetura

Um **shell host**, construído com Webpack 5, é dono das responsabilidades da
plataforma: autenticação, navegação, orquestração de rotas, controle de acesso
por papéis, error boundaries e telemetria. O mapa estático de `remotes` dele é
vazio de propósito. Em tempo de execução, ele busca um **registro** — a fonte
da verdade de rota, URL, versão, permissões e estado de cada remote — e
carrega cada remote via Module Federation na primeira vez que sua rota é
visitada.

Cinco **remotes**, cada um construído com Rsbuild, são donos do produto:
feature flags, experimentos, logs, um explorador de API e documentação. Cada
um expõe exatamente uma coisa, uma função `mount(container, props)`, e nada
mais atravessa a fronteira.

Três pacotes compartilhados mantêm o sistema coerente sem acoplar os times
entre si: os **contratos de federação**, um **pacote de UI** com primitivas e
design tokens, e um wrapper de **observabilidade** que registra quanto tempo
cada remote leva para carregar. A plataforma inteira vive num monorepo
Turborepo.

## Decisões e trade-offs

<Decision chose="Composição em tempo de execução" over="Pacotes em tempo de build">

Se o código de cada time fosse um pacote npm, o host teria que refazer build e
deploy para receber qualquer mudança, o que coloca todos os times de volta no
mesmo trem de release. Aqui o shell não importa nenhum remote de forma
estática: adicionar, desativar ou apontar um remote para outro lugar é uma
mudança no registro, e não no shell. O custo é que a integração passa a
acontecer no navegador — e é para isso que serve a próxima decisão.

</Decision>

<Decision chose="Contratos verificados duas vezes" over="Confiar na fronteira">

Em tempo de execução, uma incompatibilidade entre host e remote é uma tela em
branco. Os contratos são interfaces TypeScript, que pegam uma mudança
incompatível na compilação, e schemas Zod, que verificam os dados que de fato
chegam: o registro é validado antes de o shell lê-lo, e a função de mount de
cada remote é validada antes de o shell chamá-la.

</Decision>

<Decision chose="Router e cache isolados por remote" over="Estado global compartilhado">

Cada remote é montado com um router próprio em memória, para que o shell siga
sendo o único dono da URL, e com um cache de queries novo, para que nenhum
remote leia ou corrompa os dados de outro. Desmontar libera os dois. Os times
perdem a conveniência de mexer em estado compartilhado — e esse é justamente o
objetivo.

</Decision>

<Decision chose="Falha isolada por remote" over="Um error boundary para a aplicação">

Cada remote carrega com timeout e nova tentativa, renderiza dentro do próprio
error boundary e, se falhar, cai numa tela de nova tentativa só dele. Um
remote quebrado degrada uma rota; o shell, a navegação e todos os outros
remotes continuam funcionando.

</Decision>

<Decision chose="Uma CLI de scaffolding" over="Copiar o último remote">

O `create-mfe` gera um remote novo já configurado com Rsbuild, Module
Federation, os contratos, os design tokens compartilhados e uma estrutura de
testes com limites de cobertura. Depois, uma entrada no registro o coloca no
ar. As convenções da plataforma ficam codificadas numa ferramenta, e não em
conhecimento tribal.

</Decision>

## Resultados

Cinco remotes fazem deploy de forma independente, e publicar um não exige
nenhuma coordenação com os outros: os dois números no topo desta página são
propriedades da arquitetura, e não de uma semana boa. Responsabilidades que
cada time resolveria por conta própria — roteamento, permissões, tratamento de
falhas, telemetria, linguagem visual — são resolvidas uma vez, na plataforma.

A barra de qualidade faz parte do design, porque frontends distribuídos falham
nas fronteiras: TypeScript estrito, um teste do contrato de mount em cada
remote, limites de 80% de cobertura e uma CI rodando lint, tipos, testes e
builds em todo o monorepo.
